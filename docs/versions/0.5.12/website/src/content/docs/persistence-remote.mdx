---
title: Persistence and remote access
description: Detach from Kelpie, reattach later, use named sessions, and connect over SSH.
---

Kelpie keeps panes running in a background server. Your terminal client can detach and reconnect later.

For the local, SSH, and `kelpie --remote` workflows, see [How to work with Kelpie](/docs/how-to-work/).

## Detach and reattach

Start Kelpie:

```bash
kelpie
```

Detach the client with `ctrl+b q`.

Your panes and agents keep running. Reattach by running Kelpie again:

```bash
kelpie
```

If you want to end the session and stop its panes, stop the default server:

```bash
kelpie server stop
```

## Named sessions

Use named sessions when you want independent Kelpie servers.

```bash
kelpie session list
kelpie session attach work
kelpie session attach side-project
kelpie session stop work
kelpie session delete side-project
```

A named session has its own panes, tabs, workspaces, sockets, and runtime state. It still shares the same global config file.

Use `--json` for scripts:

```bash
kelpie session list --json
kelpie session stop work --json
kelpie session delete side-project --json
```

## Remote attach over SSH

Run Kelpie on a server and attach from any SSH client:

```bash
ssh you@server
kelpie
```

In this mode your shell is remote, Kelpie runs on the remote host, and panes keep running there after you detach.

You can also attach through SSH from your local machine:

```bash
kelpie --remote workbox
kelpie --remote ssh://you@server:2222
```

In this mode your local Kelpie is a thin client. It connects over SSH, starts or attaches to the remote Kelpie server, and streams the UI back to your local terminal.

For repeat targets, use your SSH config:

```text
Host workbox
  HostName server.example.com
  User you
  Port 2222
```

Then attach with:

```bash
kelpie --remote workbox
```

Remote attach supports Linux and macOS hosts on x86_64 and aarch64. Kelpie checks the remote platform, prefers a matching `kelpie` already on the remote `PATH`, then checks `~/.local/bin/kelpie`. If no matching binary exists, interactive runs prompt to install one to `~/.local/bin/kelpie`; non-interactive runs fail instead of modifying the host. If `~/.local/bin` is not on the remote `PATH`, Kelpie warns after install.

When your local and remote platforms match, Kelpie can copy the current local binary. Otherwise it downloads the matching release asset from `https://kelpie.example/latest.json`.

For local builds or custom binaries, set `KELPIE_REMOTE_BINARY` to a local file path before running remote attach.

```bash
KELPIE_REMOTE_BINARY=target/release/kelpie kelpie --remote workbox
```

## Remote named sessions

Use `--session` with `--remote` to attach to a named session on the remote host:

```bash
kelpie --remote workbox --session agents
```

## Direct terminal attach

Full Kelpie attach opens the whole workspace UI. Direct attach opens one server-owned terminal in your current terminal.

Attach by agent target:

```bash
kelpie agent attach reviewer
```

Attach by terminal ID:

```bash
kelpie terminal attach term_abc123
```

Direct attach streams the current rendered terminal state, then live ANSI frames. Input goes straight to that terminal.

Detach with `ctrl+b q`. Send a literal `ctrl+b` with `ctrl+b ctrl+b`.

Only one writable direct attach client owns input and resize for a terminal. Use `--takeover` to replace an existing owner:

```bash
kelpie terminal attach term_abc123 --takeover
```

## Single-process escape hatch

Use `--no-session` to run Kelpie without the background server/client split:

```bash
kelpie --no-session
```

This is mainly an escape hatch for debugging or compatibility. The default persistent session mode is the normal path.
